# 文字化け再現ビューア（`tools/mojibake/`）

- **目的**: 正しい文字列から文字化けの見た目を再現し、逆に化けた文字列から「どの文字コードをどう読み違えたか」を推定して復元する静的ツール。`test-data` が「化ける文字を出す」側なのに対し、こちらは「化けた結果から原因を逆引きする」側を担う
- **レイアウト型**: Reference系（[_common.md](_common.md) 参照）＋インタラクティブ部
- **構成**: `#tool`（化け方を見る）→ `#reverse`（原因を逆引き）→ `#why`（なぜ化けるのか）→ `#faq`
- **主要素**: `#mb-in`（元の文字列）・`.mb-preset`（`data-preset`＝`address`/`dakuten`/`kana`/`emoji`）・`#mb-warn`（変換で失われる文字の警告）・`#mb-results`（化け方カード7枚）・`#mb-bytes`（3エンコーディングのバイト列）・`#mb-rev-in`・`#mb-rev-out`（候補は最大3件、先頭は `.is-best`）

## エンコーダの作り方（このツールの肝）

ブラウザは `TextDecoder`（読む側）しか各種文字コードを持たず、**Shift_JIS や EUC-JP へ変換する機能は標準に無い**。
そこで `js/mojibake.js` の `encoderFor()` が、1バイト（0x00–0xFF）と2バイト（0x81–0xFE × 0x40–0xFE）の全パターンをデコードして
「文字 → バイト列」の逆引き表をその場で組み立て、エンコーダとして使う。初回だけ数百ミリ秒かかるので結果はキャッシュする。

## 逆引きの判定ルール

化けた文字列 `g` を各文字コードでバイト列に戻し、別の文字コードで読み直す組み合わせを総当たりする。誤答を「いちばん近い候補」として出さないため、次の枠を設けている。

- **読み方の候補から外す条件**: `g` に1文字でもその文字コードで表せない文字があれば、その読み方だった可能性はない（`missing.length` が0の組み合わせだけ残す）
- **置換文字の扱い**: `g` に U+FFFD が含まれる場合、UTF-8として読んだ結果だとは考えない（置換文字は元のバイトに対応しないため）。復元結果に U+FFFD が出る候補も捨てる
- **採点**: ひらがな+4・全角カタカナ+3・漢字+1・半角カナ−2・ラテン拡張−2・置換文字−5。**漢字の加点を弱く、半角カナの減点を強くしている**のが要点で、ここを甘くすると化けた文字列そのもの（漢字＋半角カナの羅列）が正解より高い点を取ってしまう
- **候補が出ないときの出し分け**: 置換文字や `?` を含む → 「変換の時点で文字が失われています」／1文字あたりの点が1以上 → 「化けていないようです」／それ以外 → 「見つかりませんでした」

- **挙動（E2Eで検証）**:
  - 初期表示は住所プリセットで、`#mb-results` に7枚のカードが出る。UTF-8→Shift_JIS は「譚ｱ莠ｬ驛ｽ…」の形になる
  - 絵文字プリセットにすると `#mb-warn` に「Shift_JISに存在しない文字」が出る
  - **往復テスト**: UTF-8→Latin-1 の化け文字列を `#mb-rev-in` に貼ると、元の文字列に完全復元される
  - 正常な日本語を貼ると「化けていないようです」、`?????` を貼ると「文字が失われています」になる
  - 化けの過程で U+FFFD が出ている6ケースは復元できず、その理由が表示される（できないことをできると言わない）
- **手動確認観点**:
  - 「復元できる化け」と「復元できない化け」の違いが読み手に伝わるか（`.mb-caution` と `#why` の3段落目）
  - 短い入力ではもっともらしい誤答が出うる。「いちばん近い候補」という表現以上に断定していないか
